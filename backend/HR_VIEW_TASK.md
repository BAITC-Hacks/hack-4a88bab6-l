# Задание: HR-view для Career Quest

## Цель

Реализовать простой HR-dashboard, который отвечает на три вопроса:

1. Какие навыки чаще всего проседают относительно карьерных целей сотрудников?
2. У каких сотрудников нет доступного полезного следующего шага и почему?
3. Как сотрудники участвуют в развивающих активностях и какие активности работают хуже остальных?

HR-view должен использовать эффективные текущие уровни навыков с учётом завершённых после последней оценки активностей. Сравнение выполняется с требованиями целевой роли и грейда сотрудника.

## Определения

### Целевая роль и грейд

- Если у сотрудника задан `career_goal`, использовать его `target_role` и `target_grade`.
- Если `career_goal` отсутствует, использовать следующий грейд текущей роли.
- Для сотрудника грейда Lead без `career_goal` не определять цель автоматически. Показывать такого сотрудника в списке «Не определена карьерная цель».

### Разрыв по навыку

```text
gap = max(0, required_level - effective_current_level)
```

Разрыв существует, если `gap > 0`.

### Критический разрыв

Разрыв считается критическим, если навык входит в `critical_skills` целевого профиля роли и грейда.

### Полезное доступное событие

Событие является полезным и доступным, если одновременно выполняются все условия:

- событие улучшает хотя бы один навык с целевым разрывом;
- реальный уровень навыка увеличивается с учётом `gain` и `max_level`;
- текущая роль и грейд сотрудника входят в аудиторию события;
- выполнены все `prerequisites`;
- событие не является обязательным;
- событие ранее не завершено, кроме повторяемого `EV_036`;
- для события по расписанию существует будущая сессия, либо событие имеет формат `self_paced`.

Событие, которое сотрудник может пройти, но которое не уменьшает целевой разрыв, не считается полезным следующим шагом.

## Верхние показатели

В верхней части HR-view разместить кликабельные карточки:

1. **Всего сотрудников** — количество сотрудников в загруженном наборе.
2. **С критическим разрывом** — количество сотрудников, имеющих хотя бы один критический разрыв.
3. **Без полезного следующего шага** — количество сотрудников с определённой целью и разрывами, для которых нет ни одного полезного доступного события.
4. **Без карьерной цели** — количество сотрудников, для которых нельзя определить целевой профиль.
5. **Завершение добровольных активностей** — доля `completed` среди завершённых исходов добровольных активностей:

```text
completed / (completed + dropped + no_show + declined)
```

`in_progress` не включать в знаменатель этой метрики. Рядом показывать абсолютные значения, чтобы определение показателя было понятно.

По текущему стартовому датасету ожидаемые контрольные значения:

| Показатель | Значение |
|---|---:|
| Всего сотрудников | 200 |
| С определённой целью | 190 |
| С критическим разрывом | 187 |
| Без полезного следующего шага | 30 |
| Без карьерной цели | 10 |
| Завершение добровольных активностей | около 69,5% |

После импорта дополнительных профилей значения должны пересчитываться динамически.

## Блок «Навыки с наибольшими разрывами»

Показать горизонтальную столбчатую диаграмму и таблицу навыков.

Для каждого навыка рассчитать:

- `employees_requiring_skill` — сколько сотрудников имеют этот навык в требованиях выбранной карьерной цели;
- `employees_with_gap` — у скольких из них текущий уровень ниже требуемого;
- `gap_rate` — `employees_with_gap / employees_requiring_skill`;
- `total_missing_levels` — сумма недостающих уровней по всем сотрудникам;
- `critical_gap_count` — для скольких сотрудников этот разрыв критический.

Таблица должна содержать:

| Поле | Описание |
|---|---|
| Навык | Название навыка |
| Сотрудники с разрывом | `employees_with_gap` |
| Доля с разрывом | `gap_rate` |
| Недостающие уровни | `total_missing_levels` |
| Критические разрывы | `critical_gap_count` |

По умолчанию сортировать по `employees_with_gap` по убыванию. Дать возможность сортировать по доле, недостающим уровням и критическим разрывам.

Не использовать средний абсолютный уровень навыка как основной показатель: требования различаются между ролями и грейдами.

## Блок «Разрывы по подразделениям»

Показать heatmap или компактную матрицу:

- строки — навыки;
- столбцы — подразделения;
- цвет — доля сотрудников с разрывом среди сотрудников подразделения, которым этот навык требуется.

При наведении показывать:

- количество сотрудников, которым навык требуется;
- количество сотрудников с разрывом;
- долю с разрывом;
- количество критических разрывов;
- сумму недостающих уровней.

## Блок «Сотрудники без полезного следующего шага»

Показать таблицу сотрудников, для которых нет полезного доступного события.

Колонки:

| Поле | Описание |
|---|---|
| Сотрудник | Имя и `employee_id` |
| Подразделение | Текущее подразделение |
| Текущая позиция | Роль и грейд |
| Карьерная цель | Целевая роль и грейд |
| Критические разрывы | Критические навыки с `current / required` |
| Остальные разрывы | Количество остальных разрывов |
| Причина | Почему система не может предложить шаг |

Рассчитывать одну или несколько причин:

- `career_goal_missing` — нельзя определить карьерную цель;
- `catalog_has_no_skill_event` — в каталоге нет события, развивающего нужный навык;
- `role_not_eligible` — событие существует, но недоступно текущей роли;
- `grade_not_eligible` — событие недоступно текущему грейду;
- `prerequisites_not_met` — не выполнены prerequisites;
- `already_completed` — подходящее неповторяемое событие уже завершено;
- `no_upcoming_session` — нет будущей сессии;
- `skill_cap_prevents_gain` — `max_level` события не позволяет повысить текущий уровень.

При клике на строку открывать профиль сотрудника и его карьерную траекторию.

## Блок «Участие в активностях»

Обязательные и добровольные активности показывать отдельно, чтобы compliance-обучение не искажало статистику развития.

### Распределение статусов добровольных активностей

Показать stacked bar или donut chart со статусами:

- `completed`;
- `in_progress`;
- `dropped`;
- `no_show`;
- `declined`.

По текущему стартовому датасету ожидаются:

| Статус | Количество |
|---|---:|
| Completed | 1 044 |
| No-show | 195 |
| Dropped | 160 |
| Declined | 104 |
| In progress | 16 |

### Таблица по активностям

Для каждого события показать:

- название и тип;
- формат;
- количество записей участия;
- количество `completed`, `in_progress`, `dropped`, `no_show`, `declined`;
- completion rate по завершённым исходам;
- среднюю `feedback_rating`, если оценки присутствуют;
- средний `score`, если оценки присутствуют;
- количество самостоятельных, назначенных менеджером и назначенных HR участий.

Добавить сортировку по количеству участников, completion rate, no-show и dropped.

## Фильтры

Все основные блоки должны использовать единые фильтры:

- подразделение;
- текущая роль;
- текущий грейд;
- целевая роль;
- целевой грейд;
- hard/soft skills;
- только критические разрывы;
- источник цели: `career_goal` или автоматически выбранный следующий грейд;
- формат и тип активности;
- период участия.

В MVP достаточно реализовать подразделение, роль, грейд и фильтр критических разрывов. Остальные фильтры можно добавить после основного сценария.

## Изменения backend

### Единый расчёт кандидатов

В `backend/app/service.py` создать переиспользуемую функцию `recommendation_candidates()`. Она должна возвращать только события, которые доступны сотруднику и уменьшают хотя бы один целевой разрыв.

Для каждого кандидата вернуть:

- данные события;
- список улучшаемых целевых навыков;
- текущий, требуемый и прогнозируемый уровень;
- уменьшение разрыва;
- признак критического навыка;
- количество полностью закрываемых требований;
- суммарное уменьшение разрыва.

Эту функцию должны использовать:

- recommendation context;
- OpenAI recommendation engine;
- проверка ответа модели;
- HR-summary;
- employee profile при отображении доступных следующих шагов.

### HR API

Расширить существующий `GET /api/hr/summary` либо добавить отдельные endpoints:

```text
GET /api/hr/summary
GET /api/hr/skill-gaps
GET /api/hr/employees-without-recommendations
GET /api/hr/activity-participation
```

Для MVP допустим один endpoint, возвращающий все секции одним ответом.

Предлагаемая структура:

```json
{
  "overview": {
    "employees_total": 200,
    "employees_with_target": 190,
    "employees_with_critical_gap": 187,
    "employees_without_recommendation": 30,
    "employees_without_target": 10,
    "voluntary_completion_rate": 0.695
  },
  "skill_gaps": [],
  "department_skill_gaps": [],
  "employees_without_recommendation": [],
  "activity_statuses": {},
  "activity_participation": []
}
```

Все значения должны рассчитываться из текущего `Dataset`, включая импортированные профили и историю, а также завершения, сохранённые в SQLite.

## Требования к интерфейсу

Рекомендуемая компоновка MVP:

```text
[Всего] [Critical gaps] [Без полезного шага] [Без цели] [Completion rate]

[Фильтры: подразделение | роль | грейд | только critical]

[Навыки с наибольшими разрывами]   [Heatmap по подразделениям]

[Сотрудники без полезного следующего шага]

[Статусы участия]                  [Таблица активностей]
```

Состояния загрузки, пустого результата и ошибки должны отображаться явно. При применении фильтров все показатели и графики должны обновляться согласованно.

## Приватность и ограничения

- HR-view доступен только пользователю с ролью HR.
- Не показывать публичный рейтинг сотрудников.
- Не рассчитывать общий рейтинг эффективности сотрудника.
- Не сравнивать сотрудников по месту в рейтинге.
- Индивидуальные данные показывать только в рабочем списке HR и профиле сотрудника.
- Объяснять определения метрик в tooltip или подписи.
- Не смешивать обязательные активности с добровольными в основной статистике развития.

## Критерии приёмки

1. HR видит навыки, которые чаще всего не соответствуют требованиям карьерных целей.
2. Для каждого навыка доступны количество, доля, сумма недостающих уровней и число критических разрывов.
3. HR видит сотрудников, у которых нет полезного доступного следующего шага.
4. Список «без следующего шага» строится по полезным кандидатам, а не по всем доступным событиям.
5. Для каждого сотрудника без шага указана вычисленная причина.
6. HR видит распределение статусов добровольных активностей и статистику по каждому событию.
7. Обязательные и добровольные активности разделены.
8. Фильтры подразделения, роли, грейда и критических разрывов изменяют связанные показатели.
9. Клик по сотруднику открывает его профиль.
10. Расчёты используют эффективные текущие навыки, включая завершения после последней оценки.
11. После импорта новых данных или отметки активности выполненной HR-статистика пересчитывается.
12. Для стартового датасета контрольные значения соответствуют указанным в этом документе.

## Порядок реализации

1. Вынести расчёт полезных доступных событий в `recommendation_candidates()`.
2. Исправить HR-расчёт сотрудников без следующего шага.
3. Добавить агрегаты навыков и подразделений.
4. Добавить статистику участия по событиям.
5. Расширить HR API и проверить контрольные значения.
6. Реализовать KPI-карточки, график навыков и список сотрудников без шага.
7. Добавить heatmap, таблицу активностей и фильтры.
8. Проверить обновление после completion и импорта данных.
